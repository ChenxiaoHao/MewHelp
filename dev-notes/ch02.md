## 2026-09-20 · Brainstorm 定稿

**① 用户关键原话：**

> "我要用 Superpowers 模式给现有的客服系统装上查数据的能力，用 Function Calling 让模型自己决定调什么工具——工具链要长在客服聊天本身，用户在聊天页问一句就能触发。"
> 功能需求：FastAPI+SQLAlchemy 分层骨架 / Docker 起 MySQL / 四张表灌测试数据（faq、conversations、messages、tickets，DDL 用户全文提供）/ LangChain @tool 五个业务工具（query_order、query_product、query_logistics 三个 mock，query_faq 查表，create_ticket 写工单）/ 工具基础设施（注册、Schema 校验、错误处理、超时重试、结果回灌）/ 工具链接进 SSE 聊天页（状态帧 + 工具徽章 + 落库）/ 只做单轮收敛。
> 本章不做："多轮自动循环的 Agent Loop、向量检索、RAG"。
> 验收标准：①问物流见徽章并按结果作答 ②问退货政策 faq 命中 ③问邮费漏召回是预期，记下来留给下一步升级。
> 工作要求：全程 Superpowers；聊天页改造 Vibe 例外；dev-notes/ch02.md 留痕；Context7 先查再写；选型定死走不通停下问；完结交付摘要。
> 澄清决策（AskUserQuestion）：全选推荐项——扩展现有契约 / tool_call+tool_result 双帧 / 第一轮也走流式 / 5s 超时+重试 1 次。
> 方案选择："A（推荐）"（分层扩展+自研单轮编排；B 预置 Agent 因多轮循环被否；C 同步 DB 被否）。
> 设计评审："整体方案 OK，按这个方案继续实施。实施过程中按设计里的 4 个硬性二次核对点执行：1. bind_tools + astream 的 tool call chunk 聚合先用 Context7 + 本地实际版本验证；2. create_ticket 的 conversation_id 注入机制按当前 LangChain 版本核对；3. aiomysql Windows 安装实测，不通再考虑 asyncmy；4. MySQL Docker 启动和认证兼容性实测。另外保持 Ch01 的 SSE token/done/error 兼容，不要为了 Ch02 大改 Ch01 已经稳定的代码。"

**② 关键产出：**

- Docker 环境预检：CLI 29.7.2 + Compose v5.5.0 已装，守护进程未运行（实施到 MySQL 任务前需用户启动 Docker Desktop，已告知）
